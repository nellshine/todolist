# TodoList 제품 요구사항 문서 (PRD)

버전: 1.0 / 작성일: 2026-07-29 / 작성자: 1인 개발자(PM 겸 개발 담당)

## 1. 문서 개요

### 1.1 목적
본 문서는 TodoList 애플리케이션의 제품 요구사항을 정의하여, 1인 개발자가 2일이라는
제한된 일정 내에 MVP(Minimum Viable Product)를 설계·구현·배포할 수 있도록 실행
가능한 기준을 제시한다.

### 1.2 배경
개인별로 할일(Todo)에 시작일/종료일 기간을 부여하고, 카테고리와 상태(시작 전/진행중/
완료/기한초과) 기준으로 필터링하여 관리할 수 있는 서비스가 필요하다는 문제의식에서
출발하였다. 도메인 개념, 용어, 엔티티, 비즈니스 규칙은 이미 도메인 정의서에서 확정되었으며,
본 PRD는 그 위에 비즈니스 목표, 범위, 우선순위, 기술 아키텍처, 일정을 구체화한다.

### 1.3 참조 문서
- 도메인 정의서: [`docs/1-domain-definition.md`](./1-domain-definition.md) — 용어, 엔티티, 상태 정의, 비즈니스 규칙 1~7, 유스케이스 UC-1~UC-9, 필터링 기준, 범위 외 사항의 원본(Source of Truth). 본 문서는 이를 재정의하지 않고 인용·참조한다.

## 2. 제품 목표 및 성공 지표 (KPI)

### 2.1 제품 목표
- 인증된 사용자가 개인 할일을 카테고리·기간·상태 기준으로 등록·조회·관리할 수 있는
  웹 서비스를 2일 내 MVP로 출시한다.
- 서비스 성장 시 동시접속 사용자 1,000명 규모를 감당할 수 있는 아키텍처 방향성을
  MVP 단계부터 반영한다 (실제 부하 검증은 6장/9장 참조).

### 2.2 성공 지표 (KPI)

KPI는 "MVP 출시 시점에 실측/판정 가능한 지표"와 "지금은 검증하지 않는 설계 목표"를
분리한다. 검증 불가능한 항목을 KPI로 걸어두면 성공/실패 판정이 불가능해지므로,
후자는 별도 표로 관리하고 진짜 KPI에서 제외한다.

#### 2.2.1 검증 가능한 KPI (MVP 출시 시점에 실측)

| 구분 | 지표 | 목표치 | 검증 방법 |
|---|---|---|---|
| 기능 완성도 | UC-1~UC-9 Must 항목 구현율 | 100% | Day 2 오후 수동 QA 체크리스트 통과 여부 (4장/5장 MVP 범위 기준) |
| 성능(로컬/소규모 기준) | 할일 목록 조회 API 응답시간(P95) | 300ms 이하 (개발/스테이징 환경, 단일 사용자~소수 동시 요청 기준) | 배포 전 로컬 또는 스테이징에서 브라우저 개발자도구/curl 반복 호출로 실측 |
| 동시성 최소 검증 | 소규모 동시 요청 처리 | 동시 요청 50~100건 수준에서 5xx 오류·타임아웃 0건 | 배포 전 간단한 스크립트(예: `ab`, `autocannon` 등 가벼운 도구)로 1회 스모크 테스트 |
| 안정성 | 인증 후 소유권 기반 접근 제어 위반(타 사용자 데이터 노출) 건수 | 0건 | QA 시 타 계정 리소스 ID로 접근 시도 → 404 확인 (도메인 규칙 4) |
| 일정 준수 | MVP 개발 소요 기간 | 2일 이내 | 실제 완료일 vs 계획일 비교 |

#### 2.2.2 검증하지 않는 설계 목표 (Design Goal, KPI 아님)

| 구분 | 목표치 | 비고 |
|---|---|---|
| 동시접속 처리 규모 | 1,000명 | pg Pool, stateless Express 등 아키텍처 원칙만 적용 (6장 참조). MVP 단계에서 1,000명 규모 부하테스트는 수행하지 않으며, 2.2.1의 "50~100건 스모크 테스트"로도 이 목표치를 입증하지 못함을 명확히 인지한다 |

동시접속 1,000명은 향후 확장을 염두에 둔 "설계 목표치"일 뿐, MVP 출시 시점의
성공/실패 판정 기준(KPI)으로 사용하지 않는다. 실제 1,000명 규모 검증이 필요해지면
별도 부하테스트 태스크(9장 리스크 참조)로 분리한다.

## 3. 대상 사용자

- 주 타겟: 학생, 20대~50대 직장인 등 개인 단위로 할일을 관리하고자 하는 일반 사용자
- 상세 페르소나 및 사용자 시나리오는 이번 문서 범위에서 생략한다 (요청 범위 외)
- 공통 니즈: 개인 할일을 카테고리와 기간(시작일~종료일) 기준으로 관리하고, 진행 상태별로
  빠르게 필터링해서 보고 싶어 하는 니즈

## 4. 범위 (Scope)

### 4.1 In Scope (MVP, 2일 개발 기준)
도메인 정의서 UC-1~UC-9에 대응하는 핵심 기능 전체 (상세 우선순위는 5장 참조)
- 회원가입, 로그인/인증
- 계정 정보 수정
- 카테고리 생성/수정/삭제 (기본 카테고리 자동 적용 및 이관 규칙 포함)
- 할일 등록/조회(필터링)/수정/삭제
- 할일 상태(시작 전/진행중/완료/기한초과) 파생 로직
- 웹 반응형 UI (PC/모바일 브라우저 대응)

### 4.2 Out of Scope
도메인 정의서 8장과 동일하게 아래 항목은 이번 개발 범위에서 제외한다.
- 할일 우선순위(중요도) 설정
- 마감 알림/푸시/이메일 알림
- 반복 일정(recurring todo)
- 사용자 간 할일 공유/협업
- 첨부파일, 댓글 등 부가 기능
- 소셜 로그인 등 외부 인증 연동
- 통계/리포트 대시보드

추가로, 2일 일정 제약을 고려하여 다음 사항도 이번 MVP 범위에서 제외한다.
- 네이티브 모바일 앱 (웹 반응형으로만 대응)
- 접근성(a11y) 대응 (WCAG 등 표준 준수 작업 없음)
- 자동화된 부하테스트/성능 실측 (아키텍처 설계로만 대응, 9장 참조)
- 자동화 테스트 스위트(E2E/부하) 전체 구축 — 최소한의 수동 QA만 수행

## 5. 기능 요구사항 (Functional Requirements)

도메인 정의서 6장 유스케이스(UC-1~UC-9)를 기반으로 기능 단위 요구사항을 도출하고,
MoSCoW 우선순위를 부여한다. 2일 내 완성 가능한 핵심 기능만 Must로 지정한다.

| ID | 요구사항 (연관 유스케이스) | 우선순위 | 완료 조건 (Acceptance Criteria) | 비고 |
|---|---|---|---|---|
| FR-1 | 회원가입: 이메일/비밀번호/닉네임 입력 후 계정 생성 (UC-1) | Must | 이메일 중복 시 가입 거부, 성공 시 계정이 DB에 생성되고 로그인 화면으로 이동한다 | 비밀번호 해싱 필수 (6장) |
| FR-2 | 로그인: 이메일/비밀번호 인증 후 토큰/세션 발급 (UC-2) | Must | 올바른 자격증명은 토큰 발급 후 목록 화면 진입, 틀린 자격증명은 에러 메시지와 함께 거부된다 | JWT 기반 권장 |
| FR-3 | 인증 미들웨어: 인증되지 않은 요청 차단 (도메인 규칙 1) | Must | 토큰 없이 보호된 API 호출 시 모두 401로 거부된다 (예외 없음) | 전체 API 공통 |
| FR-4 | 계정 정보 수정: 닉네임/비밀번호 변경 (UC-3) | Should | 수정 후 재조회 시 변경 값이 즉시 반영된다 | 2일 일정상 후순위, 여유 있으면 Day2에 포함 |

| FR-7 | 할일 등록: 제목/설명/카테고리(선택)/시작일자/종료일자 (UC-4) | Must | 종료일자 < 시작일자 입력 시 저장이 거부되고 에러가 표시되며, 정상 입력은 목록에 즉시 노출된다 | 시작일≤종료일 검증 (도메인 규칙 3) |
| FR-8 | 할일 목록 조회 + 카테고리 필터 + 상태 필터 (AND 조합) (UC-5, 7장) | Must | 카테고리+상태 필터를 동시에 적용했을 때 두 조건을 모두 만족하는 항목만 반환된다 (4가지 상태 필터 전부 개별 검증) | 상태는 파생값 계산 (4장) |

## 6. 비기능 요구사항 (NFR)

### 6.1 성능 및 확장성
- 목표: 동시접속 1,000명 규모까지 확장 가능한 구조를 지향한다.
- DB 커넥션: `pg`의 `Pool`을 사용해 커넥션을 재사용한다. Pool 크기는 인스턴스당
  적정 수준(예: 10~20)으로 제한하고, 커넥션 부족 시 대기열(queue)로 처리하여 DB
  커넥션 고갈을 방지한다.
- 서버 상태: Express 서버는 세션을 서버 메모리에 두지 않는 stateless 설계를 지향한다
  (인증은 JWT 등 토큰 기반으로 처리하여 서버 재시작/다중 인스턴스에도 세션 유실이
  없도록 함). 이를 통해 트래픽 증가 시 서버 인스턴스를 수평으로 추가하는 방식의
  확장이 가능해진다.
- 쿼리 최적화: ORM을 사용하지 않고 `pg`로 SQL을 직접 작성하므로, 목록 조회(FR-8)에
  자주 쓰이는 컬럼(소유자ID, 카테고리ID, 완료여부, 종료일자)에 인덱스를 설계 단계부터
  반영한다.
- 캐싱: MVP 단계에서는 별도 캐시 레이어(Redis 등)를 두지 않는다(예산/일정 제약).
  향후 트래픽 증가 시 조회 API 응답 캐싱을 확장 옵션으로 고려한다.
- 위 사항은 "설계 원칙" 수준이며, 실제 1,000명 동시접속 부하테스트는 MVP 범위 밖이다 (9장 참조).

### 6.2 보안
- 인증: JWT 기반 토큰 인증(또는 서버 세션) 적용, 인증 없는 API 접근 차단 (도메인 규칙 1, FR-3).
- 비밀번호: bcrypt 등 해싱 알고리즘으로 저장, 평문 저장 금지.
- 접근 제어: 모든 할일/카테고리 API는 소유자 검증을 수행하며, 비소유 리소스 접근 시
  403이 아닌 404로 응답하여 리소스 존재 여부를 노출하지 않는다 (도메인 규칙 4, FR-11).
- 기본적인 입력 검증(SQL 인젝션 방지를 위한 파라미터 바인딩 쿼리 사용 등)을 적용한다.

### 6.3 가용성
- 1인 개발/저예산 규모에 맞는 현실적 목표: 단일 서버 인스턴스 + 관리형(또는 로컬)
  PostgreSQL 구성 기준, 별도 이중화(HA) 없이 "일반적인 업무/개인 사용 시간대 가용성"
  수준을 목표로 한다. 24/7 무중단 SLA는 목표로 하지 않는다.
- 장애 발생 시 수동 재시작으로 복구 가능한 수준의 단순 배포 구조를 채택한다.

### 6.4 접근성
- 접근성(a11y, 스크린리더/키보드 내비게이션 등)은 이번 범위에서 고려하지 않는다.

## 7. 기술 아키텍처 개요

### 7.1 프론트엔드
- React 19 + TypeScript
- Zustand: 클라이언트/UI 상태(로그인 여부, 현재 선택된 필터, 모달/폼 상태 등 서버와
  무관한 로컬 상태) 관리
- TanStack Query: 서버 상태(할일 목록, 카테고리 목록 등 API 데이터) 관리 — 데이터
  페칭, 캐싱, 리페칭, 낙관적 업데이트(선택)를 담당하여 서버 상태와 클라이언트 상태를
  명확히 분리한다.

### 7.2 백엔드
- Node.js + JavaScript(TypeScript 미사용) + Express
- DB 접근은 `pg` 라이브러리를 직접 사용하며, Prisma 등 ORM은 사용하지 않는다.
  - 영향: SQL 쿼리를 직접 작성·관리해야 하므로 개발 속도는 ORM 대비 느릴 수 있으나,
    쿼리 최적화(인덱스 활용, N+1 방지)를 직접 제어할 수 있다.
  - 마이그레이션은 ORM 마이그레이션 도구 없이 SQL 스크립트를 수동 작성·관리한다
    (예: `db/migrations/*.sql`을 순서대로 실행하는 간단한 방식). 2일 일정 특성상
    정교한 마이그레이션 도구 도입 없이 초기 스키마 스크립트 1~2개로 관리한다.

### 7.3 데이터베이스
- PostgreSQL 17
- 핵심 테이블 방향성 (도메인 정의서 3장 엔티티 기반, 상세 컬럼 타입/제약은 별도 설계 문서에서 확정)

| 테이블 | 주요 컬럼(개략) | 비고 |
|---|---|---|
| users | id, email(unique), password_hash, nickname, created_at | 인증 기준 테이블 |
| categories | id, owner_id(FK→users), name, created_at | 사용자별 '기본' 카테고리는 회원가입 시 자동 생성 또는 애플리케이션 레벨에서 암묵 처리 (설계 시 택1) |
| todos | id, owner_id(FK→users), category_id(FK→categories), title, description, start_date, end_date, is_completed, completed_at, created_at, updated_at | 상태(시작전/진행중/완료/기한초과)는 컬럼으로 저장하지 않고 조회 시 계산 (도메인 4장) |

- 소유자ID, 카테고리ID, 완료여부, 종료일자 컬럼에 인덱스 적용을 검토한다 (6.1 참조).

### 7.4 플랫폼
- 웹 전용 서비스, 네이티브 앱 없음.
- 반응형 웹 레이아웃으로 PC/모바일 브라우저 대응 (예: 모바일 ~767px, 태블릿
  768~1023px, 데스크톱 1024px 이상과 같은 일반적인 브레이크포인트를 참고하여 CSS
  레이아웃 조정, 세부 값은 구현 시 확정).

## 9. 리스크 및 가정

### 9.1 리스크
- 자동화 테스트 부재: 2일 일정상 단위/통합 테스트 스위트를 충분히 구축하지 못하며,
  수동 QA에 의존하므로 회귀 버그 발생 가능성이 있다.
- 성능/확장성 미검증: 동시접속 1,000명 목표는 아키텍처 설계 원칙 반영 수준이며,
  실제 부하테스트(k6, JMeter 등)는 수행하지 않으므로 실사용 트래픽에서 병목이
  드러날 수 있다.
- ORM 미사용에 따른 개발 속도 저하: SQL을 직접 작성해야 하므로 스키마 변경 시
  수동 수정 범위가 넓어질 수 있다.
- 1인 개발 리소스 한계: 코드 리뷰, 페어 프로그래밍 부재로 설계/구현 오류를 조기에
  걸러내기 어렵다.
- 일정 지연 리스크: Must 항목이 예상보다 많아 Day 2 오후에 QA/배포 시간이
  압박될 수 있다 (완충 시간 명시적으로 확보되어 있지 않음).

### 9.2 가정
- 동시접속 1,000명은 향후 목표치(설계 목표)이며, MVP 출시 시점에 실제 1,000명
  동시접속이 발생한다고 가정하지 않는다.
- 인프라는 최소 비용(1인 개발 규모)의 단일 서버/DB 구성으로 가정하며, 별도의
  로드밸런서·다중 리전 구성은 이번 범위에 포함하지 않는다.
- 사용자는 웹 브라우저(PC 또는 모바일 브라우저)로 접속한다고 가정하며, 네이티브
  앱 사용자는 없다고 가정한다.
- 도메인 정의서(1-domain-definition.md)의 용어/규칙/유스케이스는 변경되지 않은
  최신 버전(v1.2)을 기준으로 한다.
