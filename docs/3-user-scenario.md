# TodoList 사용자 시나리오 문서

버전: 1.0 / 작성일: 2026-07-29

## 1. 개요

### 1.1 목적
본 문서는 PRD 3장에서 "상세 페르소나 및 사용자 시나리오는 이번 문서 범위에서 생략한다"고
명시했던 부분을 구체화한다. 목적은 개발(1인 개발자 본인)이 화면 흐름과 API 설계를 할 때
참고할 수 있도록, 실제 사용자가 어떤 순서로 기능을 사용하는지 구체적이고 현실적으로
기술하는 것이다.

### 1.2 참조 문서
- 도메인 정의서: [`docs/1-domain-definition.md`](./1-domain-definition.md) — 용어, 엔티티, 상태 정의(4장), 비즈니스 규칙 1~7(5장), 유스케이스 UC-1~UC-9(6장), 필터링 기준(7장), 범위 외 사항(8장)
- PRD: [`docs/2-PRD.md`](./2-PRD.md) — 대상 사용자(3장), 범위(4장), 기능요구사항 FR-1~18(5장), 기술 아키텍처(7장)

본 문서는 두 문서의 용어·규칙·유스케이스·요구사항 번호를 재정의하지 않고 그대로 인용한다.

### 1.3 범위
- MVP Must 기능(FR-1, 2, 3, 5, 6, 7, 8, 9, 10, 11, 12, 13)에 대응하는 핵심 사용자 흐름을 중심으로 다룬다.
- Should/Could 우선순위 기능(FR-4, 14~17)은 간략히만 다룬다.
- Won't 및 도메인 정의서 8장 범위 외 사항(알림, 반복일정, 공유, 우선순위, 통계 등)은 다루지 않는다.

## 2. 약식 페르소나

PRD 3장의 대상 사용자(학생, 20대~50대 직장인)를 이 문서 목적에 맞게 구체화한 약식 페르소나이다.
상세한 리서치 기반 페르소나가 아니라, 화면/흐름 설계를 위한 대표 사용자 상이다.

| 페르소나 | 나이대 | 핵심 니즈 |
|---|---|---|
| 지수 (대학생) | 20대 초반 | 과제 제출일, 시험 일정을 시작~종료 기간으로 등록하고, 기한이 다가오거나 지난 항목을 빠르게 확인하고 싶다 |
| 민준 (직장인) | 30대 | 업무 태스크와 개인 용무(병원, 약속 등)를 카테고리로 구분해서 관리하고, 오늘 처리해야 할 업무만 걸러 보고 싶다 |
| 하영 (이직 준비 중인 프리랜서) | 40대 | 여러 프로젝트/지원 일정을 카테고리로 나누고, 마감을 놓친 항목을 완료 처리하며 진행 상황을 정리하고 싶다 |

## 3. 핵심 시나리오

### 시나리오 1. 신규 가입 및 첫 할일 등록 (UC-1, UC-2, UC-4 / FR-1, FR-2, FR-5, FR-7)

주인공: 지수 (대학생, 처음 서비스를 접함)

1. 지수가 회원가입 화면에서 이메일/비밀번호/닉네임을 입력하고 가입을 요청한다.
   → 시스템은 이메일 중복 여부를 확인하고, 중복이 없으면 계정을 생성한 뒤 로그인 화면으로 이동시킨다 (UC-1, FR-1).
2. 지수가 이메일/비밀번호로 로그인한다.
   → 시스템은 자격증명을 검증하고 토큰을 발급한 뒤 할일 목록 화면으로 진입시킨다 (UC-2, FR-2).
3. 지수는 아직 카테고리를 만들지 않은 상태에서 "과제 제출" 할일을 등록한다. 제목, 시작일자, 종료일자만 입력하고 카테고리는 지정하지 않는다.
   → 시스템은 카테고리를 지정하지 않았으므로 '기본' 카테고리를 자동 적용하여 할일을 생성한다 (도메인 규칙 2, FR-5, UC-4).
4. 지수가 목록을 다시 조회한다.
   → 방금 등록한 할일이 '기본' 카테고리로 표시되며, 현재 날짜 기준 상태(시작 전/진행중 등)가 계산되어 함께 노출된다 (4장).

### 시나리오 2. 카테고리별로 할일 분류해서 관리 (UC-8, UC-4 / FR-5, FR-7)

주인공: 민준 (직장인, 업무/개인 용무 구분 필요)

1. 민준이 "업무" 카테고리를 생성한다.
   → 시스템은 카테고리를 생성 직후 목록/필터에 즉시 노출한다 (UC-8, FR-5).
2. 민준이 "개인" 카테고리도 하나 더 생성한다.
   → 시스템은 사용자당 여러 카테고리를 허용하므로 동일하게 생성된다 (3.2 카테고리 엔티티).
3. 민준이 "분기 보고서 작성" 할일을 등록하며 카테고리를 "업무"로 지정하고, "치과 예약" 할일을 등록하며 카테고리를 "개인"으로 지정한다.
   → 각 할일은 지정한 카테고리에 연결되어 저장된다 (UC-4, FR-7).
4. 민준이 목록을 조회하면 두 할일이 각각 지정한 카테고리 아래(또는 카테고리 필터 적용 시 구분되어)에 노출된다.

### 시나리오 3. 진행 상황 필터링으로 오늘 할 일 확인 (UC-5 / 7장 필터, FR-8)

주인공: 민준 (직장인, 출근 후 오늘 처리할 업무만 보고 싶음)

1. 민준이 할일 목록 화면에서 카테고리 필터를 "업무"로, 상태 필터를 "진행중"으로 동시에 선택한다.
   → 시스템은 두 필터를 AND 조건으로 적용해, "업무" 카테고리에 속하면서 상태가 '진행중'(완료되지 않았고 시작일자 ≤ 오늘 ≤ 종료일자)인 할일만 반환한다 (UC-5, 7장, FR-8).
2. 민준이 이어서 상태 필터를 "기한초과"로 변경한다.
   → 시스템은 "업무" 카테고리 중 완료되지 않았고 종료일자가 지난 할일만 다시 조회해 보여준다 (7장, FR-8).
3. 민준이 필터를 모두 해제한다.
   → 시스템은 민준 소유의 모든 할일을 다시 반환한다 (7장, "필터를 지정하지 않으면 사용자 소유의 모든 할일을 조회").

### 시나리오 4. 기한을 놓친 할일 처리 (도메인 규칙 6, UC-6 / FR-9, FR-12)

주인공: 하영 (프리랜서, 지난주 마감이었던 지원서 작성을 뒤늦게 마무리)

1. 하영이 목록에서 종료일자가 지난 "포트폴리오 제출" 할일을 확인한다.
   → 시스템은 완료 여부가 미완료이고 현재일자 > 종료일자이므로 이 할일의 상태를 '기한초과'로 계산해 표시한다 (4장, FR-12).
2. 하영이 실제로 작업을 마쳤으므로 해당 할일을 편집 화면에서 "완료 처리"한다.
   → 시스템은 완료 여부를 완료로 변경한다 (UC-6, FR-9).
3. 하영이 목록을 다시 조회한다.
   → 종료일자가 이미 지났음에도 불구하고, 완료 처리된 할일은 종료일자 경과 여부와 무관하게 '완료' 상태로 우선 표시된다 (도메인 규칙 6, 4장).

### 시나리오 5. 할일 수정 및 삭제 (UC-6, UC-7 / FR-9, FR-10, FR-11)

주인공: 지수 (대학생, 시험 일정이 변경됨)

1. 지수가 "중간고사 공부" 할일의 종료일자를 하루 늦게 수정하려고 편집 화면을 연다.
   → 시스템은 지수가 소유자임을 확인하고 수정 화면을 정상 노출한다 (UC-6, 도메인 규칙 4).
2. 지수가 종료일자를 변경하여 저장한다.
   → 시스템은 시작일자 ≤ 종료일자 조건을 검증한 뒤 수정 사항을 반영한다 (FR-9, 도메인 규칙 3).
3. 지수가 필요 없어진 "동아리 모임" 할일을 삭제한다.
   → 시스템은 소유권을 확인한 뒤 삭제하고, 목록에서 해당 항목을 제거한다 (UC-7, FR-10).
4. (예외 상황) 만약 지수가 URL을 조작해 다른 사용자 소유의 할일 ID로 수정/삭제를 시도하면,
   → 시스템은 해당 리소스가 존재하지 않는 것처럼 404를 반환하여 존재 여부 자체를 노출하지 않는다 (도메인 규칙 4, FR-9, FR-10, FR-11).

### 시나리오 6. 카테고리 삭제 시 할일 자동 이관 (UC-9, 도메인 규칙 7 / FR-6)

주인공: 민준 (직장인, 프로젝트 종료로 카테고리 정리)

1. 민준이 더 이상 쓰지 않는 "프로젝트A" 카테고리를 삭제한다.
   → 시스템은 카테고리를 삭제하되, 해당 카테고리에 속해 있던 할일들은 삭제하지 않는다 (도메인 규칙 7, UC-9).
2. 민준이 목록을 다시 조회한다.
   → "프로젝트A"에 속해 있던 할일들이 모두 '기본' 카테고리로 재조회되며, 데이터 자체는 유지된다 (도메인 규칙 7, FR-6).
3. (참고) 카테고리 이름만 바꾸고 싶다면, 민준은 삭제 대신 카테고리 이름 수정을 선택할 수 있다 (UC-9).

### 시나리오 7. 계정 정보 수정 (UC-3 / FR-4, Should 우선순위)

주인공: 하영 (프리랜서, 닉네임을 변경하고 싶음)

1. 하영이 마이페이지(또는 설정) 화면에서 닉네임을 변경하고 저장한다.
   → 시스템은 변경 사항을 반영하고, 재조회 시 즉시 새 닉네임이 표시된다 (UC-3, FR-4).
2. 본 기능은 Should 우선순위로, 2일 일정상 Must 기능 구현 후 여유가 있을 때 반영된다 (PRD 5장, 8장).

## 4. 예외/에러 시나리오

| # | 상황 | 시스템 반응 |
|---|---|---|
| E-1 | 할일 등록/수정 시 종료일자가 시작일자보다 빠르게 입력됨 | 저장 시점에 유효성 오류로 거부하고 할일을 생성·수정하지 않는다 (도메인 규칙 3, FR-7) |
| E-2 | 다른 사용자 소유의 할일/카테고리 ID로 조회·수정·삭제 시도 | 403이 아닌 404로 응답하여 리소스 존재 여부 자체를 노출하지 않는다 (도메인 규칙 4, FR-9~11) |
| E-3 | 인증 토큰 없이(또는 만료된 토큰으로) 보호된 API 호출 | 예외 없이 401로 거부한다 (도메인 규칙 1, FR-3) |
| E-4 | 회원가입 시 이미 가입된 이메일로 재가입 시도 | 이메일 중복으로 가입을 거부한다 (FR-1) |

## 5. 범위 외 시나리오 언급

알림/공유/반복일정/우선순위/통계 대시보드 등 도메인 정의서 8장 및 PRD 4.2의 범위 외 사항은
본 사용자 시나리오 문서에서도 다루지 않는다.
